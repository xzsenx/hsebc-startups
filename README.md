# Стартапы и вакансии — модуль поиска команды

Прототип модуля для мини-приложения Бизнес-клуба: участники размещают стартапы и вакансии,
находят друг друга в ленте и откликаются, авторы принимают решения по откликам.

Основной сценарий: Анна публикует вакансию → Максим находит её в ленте и откликается →
Анна видит отклик в кабинете и принимает его → Максим видит решение и контакт автора у себя.

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

| Что | Где |
|---|---|
| Интерфейс | http://localhost:8080 |
| API | http://localhost:8000 |
| Документация API (Swagger) | http://localhost:8000/docs |

При первом запуске пустая база заполняется демо-данными автоматически.

## Стек

- **Backend** — Python 3.12, FastAPI, SQLAlchemy 2.0, Alembic, PostgreSQL 16
- **Frontend** — React 18, TypeScript, Vite, React Router; в контейнере раздаётся nginx
- **Запуск** — Docker Compose, три сервиса: `db`, `backend`, `frontend`
- **Тесты** — pytest, 15 тестов на ключевые сценарии и права доступа

## Модель данных

```
users ──< posts ──< applications >── users
```

- **users** — участник: имя, чем занимается, телеграм, хеш пароля.
- **posts** — публикация. Поле `kind` различает стартап и вакансию: сущности
  ведут себя одинаково (лента, отклики, жизненный цикл), поэтому заводить две
  отдельные таблицы было бы дублированием. `status` — `open`/`closed`.
- **applications** — отклик: `pending` → `accepted` / `declined`, плюс `decided_at`.

Ключевое ограничение — `UNIQUE (post_id, applicant_id)`: один участник может
откликнуться на публикацию ровно один раз. Это ограничение **в базе**, а не только
проверка в коде: при двойном клике или параллельных запросах второй отклик не создастся.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/auth/register` | Регистрация, возвращает токен |
| POST | `/api/auth/login` | Вход |
| GET | `/api/auth/me` | Текущий пользователь |
| GET | `/api/posts` | Лента: фильтр `kind`, поиск `q`, пагинация |
| POST | `/api/posts` | Создать публикацию |
| GET | `/api/posts/mine` | Свои публикации |
| GET | `/api/posts/{id}` | Публикация целиком |
| PATCH | `/api/posts/{id}` | Изменить или закрыть (только автор) |
| POST | `/api/posts/{id}/applications` | Откликнуться |
| GET | `/api/posts/{id}/applications` | Отклики на публикацию (только автор) |
| GET | `/api/me/applications` | Отправленные отклики и решения по ним |
| GET | `/api/me/applications/received` | Все полученные отклики |
| PATCH | `/api/applications/{id}` | Принять или отклонить (только автор публикации) |

## Принятые решения и допущения

**Вход по почте и паролю, а не через Telegram.** Модуль задуман как часть мини-приложения,
где пользователь уже авторизован через Telegram `initData`. Для проверяемого прототипа это
неудобно: нужен бот и туннель. Поэтому сделан обычный вход, а авторизация вынесена в одно
место (`app/security.py`, `app/deps.py`) — заменить её на проверку `initData` можно, не трогая
остальной код.

**Стартап и вакансия — одна сущность с полем `kind`.** У них совпадает всё: карточка в ленте,
отклики, закрытие набора. Разница только в подписи и акцентах, поэтому разделять таблицы
означало бы дублировать и схему, и роуты.

**Лента доступна без входа, действия — нет.** Так человек видит содержимое до регистрации.
Просмотр чужих откликов и любые изменения требуют токена.

**Решение по отклику принимается один раз.** Повторное нажатие той же кнопки возвращает тот
же результат (идемпотентность, защита от двойного клика), а попытка поменять уже принятое
решение даёт 409. Иначе кандидат видел бы, как его то принимают, то отклоняют.

**Контакт автора открывается только после принятия отклика.** До этого в карточке видно имя и
род занятий, но не телеграм — иначе лента превращается в список контактов.

### Обработка повторных действий и ошибок

| Ситуация | Поведение |
|---|---|
| Повторный отклик на ту же публикацию | 409, в интерфейсе спокойное пояснение, а не красная ошибка |
| Отклик на свою публикацию | 403, кнопка отклика не показывается |
| Отклик на закрытую публикацию | 409 |
| Повторное одинаковое решение по отклику | 200, тот же результат |
| Попытка изменить решение | 409 |
| Чужая публикация или чужой отклик | 403 |
| Несуществующий id | 404 |
| Пустая лента, пустой поиск, пустой кабинет | Отдельные состояния с подсказкой, что делать |

## Безопасность

- Пароли хранятся как bcrypt-хеши, в открытом виде не хранятся и не логируются.
- Доступ проверяется **на сервере** в каждом роуте, а не скрытием кнопок в интерфейсе:
  чужую публикацию нельзя изменить и прямым запросом к API.
- Вход отвечает одинаково на «нет такой почты» и «неверный пароль» — иначе форма логина
  работает как проверка, кто зарегистрирован.
- Отклики на публикацию видит только её автор; свой отклик — только тот, кто его отправил.
- Секретов в репозитории нет: `.env` в `.gitignore`, в `.env.example` только значения-заглушки.
  `JWT_SECRET` по умолчанию годится лишь для локального запуска, для продакшена его нужно заменить.
- Длины всех текстовых полей ограничены на уровне схемы, пагинация ограничена сверху.

## Тесты

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Тесты идут на SQLite — чтобы запускались без Docker. Покрыты: основной сценарий целиком,
повторный отклик, отклик на свою и на закрытую публикацию, доступ постороннего к чужим
откликам и публикации, идемпотентность решения, фильтры и поиск в ленте, отличие ответов
логина при неверном пароле.

## Структура

```
backend/
  app/
    main.py          точка входа, CORS, подключение роутеров
    config.py        настройки из переменных окружения
    database.py      подключение к БД, сессии
    models.py        таблицы
    schemas.py       входные и выходные схемы (pydantic)
    security.py      хеширование паролей, JWT
    deps.py          зависимости: сессия БД, текущий пользователь
    seed.py          демо-данные для пустой базы
    routers/         auth, posts, applications
  alembic/           миграции
  tests/             pytest
frontend/
  src/
    lib/api.ts       весь доступ к API в одном месте
    lib/auth.tsx     состояние авторизации
    pages/           лента, публикация, создание, кабинет, вход
    components/ui.tsx общие элементы и состояния
    styles.css       стили, светлая и тёмная тема
```

## Интерфейс

Одна вёрстка на телефон и компьютер: лента в одну колонку на узком экране и в две от 720px,
элементы управления не уезжают за край, поля ввода 16px (иначе iOS зумит форму при фокусе).
Поддержана тёмная тема через `prefers-color-scheme`.
